## Capability observability on every model-call branch in `BaseAgentRunner`

Every execution branch in `sinan_agentic_core/core/base_runner.py` that issues a model call and accepts a capability list must surface a capability hook on that branch:

- Branches that delegate to `Runner.run(...)` / `Runner.run_streamed(...)` must build the hook bundle via `self._build_hooks(capabilities)` and pass it as `hooks=` when non-empty — matching the `_execute_basic` and `_execute_streamed` shape.
- Branches that bypass the SDK and call the OpenAI client directly (e.g. the summarize-and-extract recovery branch inside `_execute_with_fallback`) must invoke dedicated `Capability` hooks (`on_fallback_start` / `on_fallback_end`, plus any future equivalents added for new bypass branches) for every registered capability — once before the call and once after the response, before any output parsing.

When adding a new execution branch, modifying an existing one, or reviewing changes that touch a model-call site, confirm the capability hook surface reaches that branch. Silent observability gaps do not raise at runtime.

**Why:** Two sibling regressions on the same class.

- Issue #29 — `_execute_with_fallback`'s normal-execution branch dropped the `hooks=` kwarg on its `Runner.run` call, silencing every `on_agent_start` / `on_tool_start` / `on_tool_end` callback on that path. Sibling paths `_execute_basic` and `_execute_streamed` had the wiring; the third drifted. The SDK accepts the missing kwarg and runs without callbacks, so the regression did not raise.
- Issue #30 — the recovery branch of `_execute_with_fallback` ran outside the SDK lifecycle entirely (a direct `AsyncOpenAI` chat-completions call). Audit-log, output-validator, and reliability-monitoring capabilities silently missed every rescued run — typically the runs that nearly failed and are operationally the most interesting. The fix added explicit `on_fallback_start` / `on_fallback_end` hooks invoked directly by the runner, since SDK lifecycle hooks cannot reach a branch that does not go through `Runner.run`.

**How to apply:** For SDK-delegating branches, use the `run_kwargs: dict[str, Any] = {...}` pattern from `_execute_basic` (`base_runner.py:324`): build `hooks = self._build_hooks(capabilities)`, then `if hooks: run_kwargs["hooks"] = hooks` before calling `Runner.run(**run_kwargs)`. For SDK-bypassing branches (direct chat-completions, future provider-specific escape hatches), declare a matched pair of hooks on the `Capability` protocol (default no-op) and loop `for cap in capabilities: cap.on_<event>(ctx_wrapper, ...)` immediately before and after the bypass call — see `base_runner.py:400` (`on_fallback_start`) and `base_runner.py:462` (`on_fallback_end`) for the established pattern. Do not fire tool-event hooks on a bypass branch when no tools are invoked there — that produces misleading telemetry.

## Reuse the configured default OpenAI client on every SDK-bypassing branch in `BaseAgentRunner`

Any execution branch in `sinan_agentic_core/core/base_runner.py` that issues a model call outside `Runner.run(...)` / `Runner.run_streamed(...)` (e.g. the summarize-and-extract recovery branch inside `_execute_with_fallback`) must obtain its OpenAI client from `resolve_openai_client()` (`sinan_agentic_core/llm/factory.py`) — the owned wrapper that reads back the client `configure_llm_provider(...)` installed via `set_default_openai_client(...)`, and builds a bare `AsyncOpenAI()` only when no provider has been configured. Do not construct a client at the call site, do not read provider keys, endpoints, or deployment names directly, and do not call `AsyncOpenAI(api_key=get_default_openai_key())`.

`resolve_openai_client()` is also the only place in the codebase allowed to import `agents.models._openai_shared` — `openai-agents==0.18.3` exports `set_default_openai_client` from the `agents` root but no matching getter, so reading the client back needs the private module. Confining that import to the module that already owns the setter side keeps the SDK-private surface at one site instead of one per call site (CLAUDE.md rule 5: consumers must not reach into `agents.*` internals). Re-check for a public getter when the SDK version bumps.

**Why:** Issue #35 — the recovery branch built `AsyncOpenAI(api_key=get_default_openai_key())`, bypassing the configured default. Under `AzureOpenAIProviderConfig`, `configure_llm_provider` (`sinan_agentic_core/llm/factory.py:42`) installs an `AsyncAzureOpenAI` via `set_default_openai_client(...)` but never sets a default key, so the rescue call crashed at client construction with `OpenAIError: The api_key client option must be set...`. Under plain OpenAI it masked itself whenever `OPENAI_API_KEY` was exported in the environment, which is why CI stayed green and the regression only surfaced on the first Azure-hosted evaluation. The framework's contract is that `configure_llm_provider` is the single point that owns provider-specific client wiring; any model-call site that rebuilds its own client breaks that contract.

**How to apply:** One call, at the top of the bypass branch:

```python
from ..llm import resolve_openai_client

client = resolve_openai_client()
```

Apply this on every new SDK-bypassing branch — current and future — including recovery, repair, summarize-and-extract, and any provider-specific escape hatch added later. Tests that need to inject a stub client patch the resolver at its import site (`patch("sinan_agentic_core.core.base_runner.resolve_openai_client")`), not `openai.AsyncOpenAI` — the branch no longer constructs a client, so patching the constructor injects nothing. Tests for the resolver itself patch `sinan_agentic_core.llm.factory.get_default_openai_client`.

## Run-level SDK kwarg wiring on every `Runner`-calling site in `sinan_agentic_core`

Every call site anywhere in `sinan_agentic_core/` that calls `Runner.run(...)`, `Runner.run_streamed(...)`, or builds `agent.as_tool(...)` kwargs must route each per-run SDK setting through its own `_build_*`/`build_*` helper and set the corresponding kwarg when the helper returns non-`None` — whether that call site is a branch inside `BaseAgentRunner` or a standalone function elsewhere in the package. The same discipline applies one level down: when a per-run setting is built by more than one `_build_run_config`-shaped or `_build_error_handlers`-shaped function (one per call-site family), adding that setting to one function does not add it to its siblings — each must be checked independently. Confirmed sites: issue #41's `self._build_run_config(agent_def)` → `run_config=` on all five `base_runner.py` branches (`_execute_basic` `:332`, `_execute_with_fallback` `:384`, `_execute_streamed` `:533`, the `as_tool` sub-agent branch `:780`, `run_agent()` `:699`); issue #42's `self._build_error_handlers(agent_def)` → `error_handlers=` on the four `Runner.run`/`Runner.run_streamed` branches (`_execute_basic` `:338`, `_execute_with_fallback` `:398`, `_execute_streamed` `:553`, `run_agent()` `:723`); issue #59's `build_run_config(resolved)` → `run_config=`, wired on all three `services/chat.py` functions (`chat()` `:137-139`, `chat_with_hooks()` `:214-216`, `chat_streamed()` `:298-300`) — call sites that are not `BaseAgentRunner` branches at all; issue #80's `tool_output_trim` setting, present in `BaseAgentRunner._build_run_config` (`base_runner.py:883-907`) but missing from the sibling `run_config.build_run_config()` (`run_config.py:37-66`) that `services/chat.py` calls — the same setting, wired on one `_build_run_config`-shaped function and not its sibling, rather than missing from a `Runner.run` call site entirely; and issue #89's `invalid_output_recovery` flag, read directly off `agent_def.invalid_output_recovery` in `BaseAgentRunner._build_error_handlers` (`base_runner.py:914-932`) but absent from the sibling `output_recovery.build_error_handlers(agent)` (`output_recovery.py:175-201`) that `services/chat.py`'s three functions and any direct `Runner.run()` caller use — the same sibling-function gap as issue #80, this time on the `error_handlers`-building pair instead of the `run_config`-building pair.

When adding a new execution branch, a new `_build_*`/`build_*` helper for a new per-run SDK setting, or a new module anywhere in `sinan_agentic_core/` that calls `Runner.run`/`Runner.run_streamed`/`as_tool`, confirm the setting reaches every such call site in the package — not just the ones under active development, and not just the ones inside `base_runner.py`. Also confirm it reaches every other function that assembles a `RunConfig`/`error_handlers` for a different call-site family (currently `BaseAgentRunner._build_run_config` / `run_config.build_run_config`, and `BaseAgentRunner._build_error_handlers` / `output_recovery.build_error_handlers` — check both members of a pair when either changes). A branch marked deprecated or "kept for backward compatibility" is not exempt: it still calls the SDK and still needs the setting, or its outputs silently diverge from the other branches.

**Exception — genuine SDK gaps, not oversights:** a call site is not in violation if the underlying SDK call does not accept the kwarg for that call shape. Verify this against the installed SDK version — do not assume — then document the gap inline with a `NOTE:` comment at the call site naming the SDK method and version checked, so a future reviewer (or `/check-code-quality`) can tell a real limitation apart from a missed wiring site. Issue #42: `Agent.as_tool()` accepts `run_config` (wired at `:804-806`) but has no `error_handlers` parameter in `openai-agents==0.18.3`, so the `as_tool` branch is correctly left out of `_build_error_handlers` wiring, documented at `base_runner.py:808-811`. Re-check when the SDK version bumps.

**Why:** Issue #41 — `_build_run_config` (pre-approval for tool-input guardrails) was wired onto `_execute_basic`, `_execute_with_fallback`, `_execute_streamed`, and the `as_tool` branch, but `run_agent()` — kept only for backward compatibility — was left out on the first pass. `check-code-quality` failed twice citing the identical gap (`run_agent() ... without run_config wiring`) before a third pass wired it. Issue #42 is a second, independent instance of the same class: a new helper (`_build_error_handlers`) needed the identical per-branch wiring, and this time landed correctly on the first pass — but its one skipped branch (`as_tool`) needed to be told apart from a repeat of the #41 gap. Issue #59 is a third instance, one level up: the identical per-run setting (tool-input pre-approval) needed the identical wiring discipline on `services/chat.py`'s three functions, which are not `BaseAgentRunner` branches — a call site family this rule's wording did not previously name. It landed correctly on the first pass by reusing the extracted `build_run_config()` helper, but a rule worded exclusively around `base_runner.py` risks a future contributor concluding that a new `Runner`-calling module elsewhere in the package is exempt, since it is not a "branch in `BaseAgentRunner`". Issue #80 is a fourth instance, and a narrower failure mode within the same class: `BaseAgentRunner._build_run_config` already resolved `tool_output_trim` via `_build_tool_output_trimmer`, but the standalone `run_config.build_run_config()` — the exact helper issue #59 wired into `services/chat.py` — had no equivalent branch, so an agent resolved through `chat()`/`chat_with_hooks()`/`chat_streamed()` ran untrimmed while the identical agent run through `BaseAgentRunner` was trimmed. The drift was not a missing call site (the call site was already correct) but a second `_build_run_config`-shaped function that lagged behind its sibling on a setting the first already had. The fix extracted the SDK-filter translation into a shared `build_tool_output_trimmer()` (`core/tool_output_trim.py:84-102`), imported by both functions, so future settings added to one route through the same shared translator rather than being reimplemented — but the wiring decision (which `config_kwargs` key each function sets) still lives separately in each function and still needs checking by hand. Issue #89 is a fifth instance, the same narrower failure mode as #80 but on the `error_handlers`-building pair instead of the `run_config`-building pair: `BaseAgentRunner._build_error_handlers` already read `invalid_output_recovery` off `agent_def` on every execution branch, but the standalone `output_recovery.build_error_handlers(agent)` that `services/chat.py` and any direct `Runner.run()` caller use had no equivalent check, so an agent declaring `invalid_output_recovery: false` failed loudly under `BaseAgentRunner` and was silently recovered under `chat()`. Because the standalone function only holds a built `Agent`, not the `agent_def` its sibling has, the fix resolved the flag by looking the definition up through `get_agent_registry().get(agent.name)` — the same by-name pattern issue #80 established for `_declared_tool_output_trim` in `run_config.py:93-104` — rather than inventing a second mechanism. This is now the fifth distinct per-call-site concern to require this discipline — see the capability-hook and client-reuse entries above in this file — because the class spans multiple near-duplicate `Runner`-calling sites and multiple near-duplicate `RunConfig`/`error_handlers`-building functions, with no shared mechanism that enforces a new per-run setting reaches all of them.

**How to apply:** Use the pattern at `base_runner.py:332-334` (`_execute_basic`, `_build_run_config`), `:338-344` (`_build_error_handlers`), or `services/chat.py:137-139` (`chat()`, `build_run_config`): `<setting> = self._build_<setting>(agent_def)` (or `build_<setting>(agent)` outside `BaseAgentRunner`); `if <setting> is not None: run_kwargs["<kwarg>"] = <setting>`, placed before the `Runner.run(**run_kwargs)` / `Runner.run_streamed(**run_kwargs)` / `tool_agent.as_tool(**as_tool_kwargs)` call. Before shipping any new `_build_*`/`build_*` helper or per-run SDK setting, grep the whole package — `grep -rn 'Runner\.run(\|Runner\.run_streamed(\|as_tool_kwargs' sinan_agentic_core/` — not just `base_runner.py`. Every hit must either carry the new kwarg or a `NOTE:` comment citing the specific SDK method/version that lacks the parameter. Additionally, when a new setting is added to one member of a sibling pair — `BaseAgentRunner._build_run_config` / `run_config.build_run_config`, or `BaseAgentRunner._build_error_handlers` / `output_recovery.build_error_handlers` — check the other by name (`grep -rn 'def build_run_config\|def _build_run_config\|def build_error_handlers\|def _build_error_handlers' sinan_agentic_core/core/`) and confirm both resolve the same settings. A standalone sibling that only receives a built `Agent` (not the `agent_def` its `BaseAgentRunner` counterpart holds) resolves definition-level settings by looking the registered definition up via `get_agent_registry().get(agent.name)` — see `_declared_tool_output_trim` (`run_config.py:93-104`) and `_recovery_opted_out` (`output_recovery.py:217-228`) — not by inventing a new lookup path per setting. Extract any new SDK-translation logic into a shared function in the relevant `core/*.py` module (e.g. `core/tool_output_trim.py`) so both call it instead of each reimplementing it.

## Translate a declared config into SDK settings via a module-level function beside the Pydantic model, not a private `BaseAgentRunner` method

Every `core/*.py` module that defines a Pydantic model translating a YAML-declared setting into an `agents.*` SDK object — `model_retry.py`'s `ModelRetryConfig`, `tool_output_trim.py`'s `ToolOutputTrimConfig`, and (once they gain the same treatment) `turn_budget.py`'s and `tool_error_recovery.py`'s config models — must expose that translation as a module-level `build_*` function declared beside the model, not as a private method on `BaseAgentRunner`. When a second caller — an overlay helper in the same module, a different execution branch, an SDK-bypassing runner branch — needs the same translated object, it imports the module-level function; it does not gain its own `_build_*` method on `BaseAgentRunner` that reimplements the same `if config is None: return None` / `.build()` (or equivalent) check inline.

This is narrower than the run-level SDK kwarg wiring rule above: that rule governs whether a *per-run setting* reaches every `Runner.run`-calling site; this one governs where the *single-value translation* for one config model lives once a second caller needs it. A `_build_*` method that only assembles several already-translated values into one kwarg bundle (`_build_run_config`, `_build_error_handlers`) is not in scope here — only a method that duplicates a config model's own `is None` / `.build()` translation is.

**Why:** Issue #80 first established this shape: `build_tool_output_trimmer()` (`core/tool_output_trim.py:84`) is the shared translator both `BaseAgentRunner._build_run_config` and the standalone `run_config.build_run_config()` call. Issue #90 repeated the same fix one config module over: `BaseAgentRunner._build_model_retry()` reimplemented the identical `if agent_def.model_retry is None: return None; return agent_def.model_retry.build()` check that `model_retry.apply_model_retry()` already performed inline — one check, written twice, because the SDK-bypassing overflow-fallback branch inside `_execute_with_fallback` needed the translated settings and had no shared place to get them from except its own private method. The fix in both cases was identical: extract the translation into a module-level function beside the config's Pydantic model (`build_model_retry_settings()`, `core/model_retry.py:116`), delete the runner's private duplicate, and have every caller — the overlay function and the bypass branch alike — import the shared function instead. As of this writing, two of the four declarative SDK-config modules (`turn_budget.py`, `tool_error_recovery.py`) still lack this treatment and are tracked separately (issues #94, #95) — a rushed fix on either is exactly where a third private-method duplicate on `BaseAgentRunner` would get written next.

**How to apply:** Before adding a private `_build_*` method to `BaseAgentRunner` that translates a `core/*.py` Pydantic config into an SDK object, check whether the config module already exposes — or should expose — a module-level `build_*` function for that translation; see `build_model_retry_settings()` (`core/model_retry.py:116`) and `build_tool_output_trimmer()` (`core/tool_output_trim.py:84`) for the pattern. If it does not exist yet, add it there instead of on the runner. Keep it unexported from `core/__init__.py` while every caller stays in-package, matching both current instances. The function's parameter is the config value itself (`retry: ModelRetryConfig | None`), not the enclosing `agent_def` — a signature narrower than the runner's original private method, so callers that only have the config value (not a full `agent_def`) can use it directly. This applies whenever a second caller needs a translation that already exists somewhere as inline logic, not only when authoring a brand-new config module — including when issues #94/#95 land on `turn_budget.py`/`tool_error_recovery.py`.

## Verify claims about a wrapped SDK object's behavior before asserting them in a validator or doc

Any `Field` constraint, `model_validator`, error message, docstring, or README paragraph that asserts what a wrapped `agents.*` object does or does not do with a given input must be checked against the installed SDK's actual behavior — read its source or drive the real object through a representative input — before being written. Do not derive the claim from how the object's name or parameters suggest it "should" behave.

**Why:** Issue #46 — `ToolOutputTrimConfig` (`sinan_agentic_core/core/tool_output_trim.py`) added a cross-field validator rejecting any policy where `preview_chars >= max_output_chars`, on the premise that such a preview "never shortens an output." The premise was never checked against `agents.extensions.ToolOutputTrimmer`: the SDK compares the assembled replacement's length to the *original tool output's* length, not to `max_output_chars`, so `preview_chars == max_output_chars == 500` still collapsed a 100,000-character output to 566 characters. The same false premise was written four times — the validator's error message, its docstring, `README.md`, and a test docstring — before a reviewer measured the real filter against the installed SDK and found the rejected configuration was one of the most natural policies to express (`preview_chars: 500` with `max_output_chars: 500`, "keep the first 500 characters of anything bigger"). The wrapper ended up more restrictive than the library it wraps, on a claim that did not hold, and the same unverified claim was carried into three more artifacts before anyone tested it.

Issue #69 repeated the same shape one level up, in a usage-example comment rather than a validator: `README.md`'s `chat_streamed` example for a `model_refusal` payload showed `{"error": "I can't help with that."}`, but `ModelRefusalError` renders as `Model refused to produce output: <refusal>` (verified against `openai-agents==0.18.3`, `agents/exceptions.py`). Nobody had checked the exact rendered text against the installed SDK before writing it into the doc — the same unverified claim as issue #46, just in a top-level README example instead of a `core/` config validator.

**How to apply:** Before adding a validator, `Field` constraint, docstring, or doc paragraph in `sinan_agentic_core/core/` that says a wrapped SDK object "always," "never," or "would never" does something with valid input, drive the installed object through that input in a throwaway script or a test and read the actual result. This applies to every module that translates a YAML-declared config into an SDK class — `tool_output_trim.py`, `model_retry.py`, `tool_error_recovery.py`, and future siblings — whenever the config layer adds a constraint the SDK class itself does not enforce. This is the same discipline as the SDK-version-gap exception in the entry above, applied to behavior instead of parameter presence: verify against the installed package first, then write the claim once it is confirmed true.

The same check applies outside `core/` and outside validators: any doc paragraph, docstring, or usage-example comment anywhere in the repo — `README.md` included — that shows the literal string a wrapped `agents.*` exception or object renders must be verified against the installed SDK version before being committed. See `core/run_errors.py`'s `run_error_payload()`, whose `error` value is `str(error)` on whatever the SDK raised, and the README's `chat_streamed` `model_refusal` example it feeds, for the pattern: render the real exception through the installed package, then quote that text exactly rather than a plausible-sounding guess.

## Parse a fully-defaulted optional YAML config block with `is not None`, never a truthiness check

Any code in `sinan_agentic_core/registry/` that builds a Pydantic model from an optional block in `agents.yaml`/`tools.yaml` — where the model itself has no required fields — must guard on `block is None`, not `if block:`/`if block else None`. Route it through `_parse_optional_block()` (`sinan_agentic_core/registry/agent_catalog.py:268-283`) rather than reimplementing the check inline. Where the block is already declared as an optional model field on the catalog's resolved entry — `ToolYamlEntry.mcp: ToolMCPConfig | None` (`sinan_agentic_core/registry/tool_catalog.py:59`) — read it off the resolved entry (`self.get(name).mcp`) instead of re-parsing the raw dict: the field declaration already applies the rule, and going through it also validates the block's own fields. An empty mapping (`{}`) is a valid declaration meaning "enable this with the model's defaults"; a truthiness check treats it as absent, which is a different, wrong behavior for a model that has no required fields.

**Why:** Issue #66 — `AgentCatalog.get()` parsed three optional blocks off the same raw agent entry. `tool_output_trim` correctly guarded on `raw_trim is not None`; the two siblings four lines above, `turn_budget` and `model_retry`, guarded on plain truthiness (`if raw_budget else None`), so `turn_budget: {}` / `model_retry: {}` silently opted an agent *out* of a feature its author had just written to opt it *into* — both `TurnBudgetConfig` and `ModelRetryConfig` are fully defaulted, so the empty mapping is a meaningful declaration, not an absence. The correct rule already existed once in the same function; writing it three separate times let two of the three drift from it. The fix collapsed all three call sites into one `_parse_optional_block()` helper so the rule exists once, not per call site.

Issue #81 is the same shape in the sibling catalog: `ToolCatalog.get_mcp_tools()` read the `mcp` block off the raw dict as `if mcp_raw and mcp_raw.get("expose", False)`, even though `ToolYamlEntry.mcp` four lines up already declares that block as `ToolMCPConfig | None`. Because `ToolMCPConfig.expose` defaults to `False`, the empty-mapping case produced the same list either way — but the inline read bypassed the model, so `expose` was tested for truthiness rather than validated: `expose: "no"` exposed a tool its author had turned off, and `expose: "maybe"` exposed it silently instead of raising. The fix deleted the raw read and resolved through `self.get(name).mcp`, which removed the last inline copy of the rule in `registry/`.

**How to apply:** When adding a new fully-defaulted optional config block anywhere `AgentCatalog` or `ToolCatalog` parse `agents.yaml`/`tools.yaml`, call `_parse_optional_block(raw, key, Model)` instead of writing a new inline `raw.get(key)` plus truthy check — or, when the catalog's resolved entry already declares the block as an optional model field, read it from that entry and drop the raw-dict access entirely. Do not extend this to a block collected as a *list or set of members* rather than validated as a single model — `capabilities` and `tool_rules` genuinely mean "nothing declared" when empty, not "opt in with defaults." The rule applies only when an empty mapping and the model's own defaults express the same declaration. Before shipping a change in `registry/`, `grep -rn 'raw\.get(\|_raw_tools\[\|_raw_agents\[' sinan_agentic_core/registry/` and confirm no optional single-model block is read for truthiness outside `_parse_optional_block()` or a resolved entry's field.

## Read a Registry through its own public accessors, never its private dict

Code outside `sinan_agentic_core/registry/` must not read a `Registry` class's leading-underscore attribute (`ToolRegistry._tools`, `AgentRegistry._agents`, `GuardrailRegistry._guardrails`) directly. If an existing public accessor covers the need (`get`, `get_all_functions`, `get_tool_functions`, `list_names`, `list_all`), call it. If none fits, add the accessor to the registry class itself — in `sinan_agentic_core/registry/` — rather than reaching past it. Do not add an accessor with no caller; add exactly the one the call site needs.

**Why:** Issue #58 — `BaseAgentRunner.__init__` built `tool_map` by comprehending over `self.tool_registry._tools.items()` (`base_runner.py:75`), and `_build_tools()`/`_build_handoffs()` checked membership and fetched definitions via `self.agent_registry._agents` at three more sites (`:821`, prior duplicate lookup, and `:980`), instead of the registry's own `.get()`. All four were the last sites in a repo-wide sweep tracked from epic #39 through #41: after the fix, `ToolRegistry` gained `get_all_functions()` (mirroring the pre-existing `GuardrailRegistry.get_all_functions()`), and both call sites in `base_runner.py` switched to `AgentRegistry.get(name)`. A grep across `sinan_agentic_core/` and `examples/` after the fix found zero remaining `_tools`/`_agents`/`_guardrails` reads outside the registry modules that own them — confirming the class of mistake, not a one-off.

**How to apply:** Before writing new code in `sinan_agentic_core/core/`, `sinan_agentic_core/registry/agent_factory.py`, or `examples/` that inspects a `ToolRegistry`, `AgentRegistry`, or `GuardrailRegistry` instance, check for an existing public accessor first — see `ToolRegistry.get_all_functions()` (`registry/tool_registry.py:60-62`) and `AgentRegistry.get()` (`registry/agent_registry.py:65-67`) for the pattern each new accessor should follow. This rule applies only to this codebase's own `Registry` classes — it does not cover third-party objects (e.g. the MCP SDK's `server._tool_manager._tools`, tracked separately under the SDK-internals sweep). Before shipping, `grep -rn '\._tools\b\|\._agents\b\|\._guardrails\b' sinan_agentic_core/ examples/` and confirm every hit is inside `sinan_agentic_core/registry/`.

## Access a third-party SDK object through its public API, never a leading-underscore attribute

Code anywhere in this repo — tests included — that reads an attribute or calls a method on an object owned by a third-party package (`mcp.server.fastmcp.FastMCP`, `agents.*`, or any future SDK dependency) must not touch a name starting with `_` on that object. Check the SDK's public surface first — a listing method, a getter, a documented accessor that returns the same information a real client of that SDK would see. If a public equivalent exists, use it even when it costs an `await` or a slightly less direct read. If no public equivalent exists, the private read is unavoidable, but confine it to exactly one function or module that owns the exception and document why inline — do not repeat the private import or attribute read at every call site that needs the value.

**Why:** Issue #75 — six sites across `tests/test_mcp/test_server_builder.py` (`:112,131,149,165,187,204,224`) read `server._tool_manager._tools` and called a tool's handler via `discover_tool.fn(...)` directly, coupling the tests to the MCP SDK's internal `ToolManager` layout instead of the public contract an actual MCP client uses. Both had public equivalents on `mcp==1.27.0` (`await server.list_tools()`, `await server.call_tool(name, args)`), so the fix replaced every private read outright; a repo-wide `grep -rn '_tool_manager\|_resource_manager\|_prompt_manager'` confirmed zero remaining sites. Issue #74 is the adjacent case where no public equivalent existed: `resolve_openai_client()` (`sinan_agentic_core/llm/factory.py:25`) needs to read back the client `set_default_openai_client(...)` installed, but `openai-agents==0.18.3` exports the setter with no matching public getter, so reading it back required importing the private `agents.models._openai_shared` module. That fix did not avoid the private import — it isolated it to the one wrapper function every caller routes through, instead of importing the private module at each call site. The Registry-internals rule above already flagged this repo's own `Registry` classes as a distinct, narrower case and pointed at "the SDK-internals sweep" as a separate concern — this entry is that sweep's rule.

**How to apply:** Before writing test or production code that reads a `_`-prefixed attribute or calls a `_`-prefixed method on a third-party object, check the SDK's public API (its documented methods, or its `__all__`/exported symbols — not a guess) for an equivalent. Prefer the public call even in tests, mapping return values into the shape the test needs (see `listed_tools()`, `tests/test_mcp/test_server_builder.py`, which maps `await server.list_tools()` by name). If genuinely no public equivalent exists, confine the private read to one owned wrapper — see `resolve_openai_client()`, `sinan_agentic_core/llm/factory.py` — and have every other call site import the wrapper, not the private SDK symbol. Before shipping a change that touches a third-party SDK object, `grep -rn '\._tool_manager\|\._resource_manager\|\._prompt_manager\|agents\.models\._openai_shared\|agents\._'` (extend the pattern for any newly adopted SDK) across the changed files and confirm no sibling private-access site was missed.
