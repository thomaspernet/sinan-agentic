## Capability observability on every model-call branch in `BaseAgentRunner`

Every execution branch in `sinan_agentic_core/core/base_runner.py` that issues a model call and accepts a capability list must surface a capability hook on that branch:

- Branches that delegate to `Runner.run(...)` / `Runner.run_streamed(...)` must build the hook bundle via `self._build_hooks(capabilities)` and pass it as `hooks=` when non-empty — matching the `_execute_basic` and `_execute_streamed` shape.
- Branches that bypass the SDK and call the OpenAI client directly (e.g. the summarize-and-extract recovery branch inside `_execute_with_fallback`) must invoke dedicated `Capability` hooks (`on_fallback_start` / `on_fallback_end`, plus any future equivalents added for new bypass branches) for every registered capability — once before the call and once after the response, before any output parsing.

When adding a new execution branch, modifying an existing one, or reviewing changes that touch a model-call site, confirm the capability hook surface reaches that branch. Silent observability gaps do not raise at runtime.

**Why:** Two sibling regressions on the same class.

- Issue #29 — `_execute_with_fallback`'s normal-execution branch dropped the `hooks=` kwarg on its `Runner.run` call, silencing every `on_agent_start` / `on_tool_start` / `on_tool_end` callback on that path. Sibling paths `_execute_basic` and `_execute_streamed` had the wiring; the third drifted. The SDK accepts the missing kwarg and runs without callbacks, so the regression did not raise.
- Issue #30 — the recovery branch of `_execute_with_fallback` ran outside the SDK lifecycle entirely (a direct `AsyncOpenAI` chat-completions call). Audit-log, output-validator, and reliability-monitoring capabilities silently missed every rescued run — typically the runs that nearly failed and are operationally the most interesting. The fix added explicit `on_fallback_start` / `on_fallback_end` hooks invoked directly by the runner, since SDK lifecycle hooks cannot reach a branch that does not go through `Runner.run`.

**How to apply:** For SDK-delegating branches, use the `run_kwargs: dict[str, Any] = {...}` pattern from `_execute_basic` (`base_runner.py:324`): build `hooks = self._build_hooks(capabilities)`, then `if hooks: run_kwargs["hooks"] = hooks` before calling `Runner.run(**run_kwargs)`. For SDK-bypassing branches (direct chat-completions, future provider-specific escape hatches), declare a matched pair of hooks on the `Capability` protocol (default no-op) and loop `for cap in capabilities: cap.on_<event>(ctx_wrapper, ...)` immediately before and after the bypass call — see `base_runner.py:400` (`on_fallback_start`) and `base_runner.py:462` (`on_fallback_end`) for the established pattern. Do not fire tool-event hooks on a bypass branch when no tools are invoked there — that produces misleading telemetry.

## Reuse the configured default OpenAI client on every SDK-bypassing branch in `BaseAgentRunner`

Any execution branch in `sinan_agentic_core/core/base_runner.py` that issues a model call outside `Runner.run(...)` / `Runner.run_streamed(...)` (e.g. the summarize-and-extract recovery branch inside `_execute_with_fallback`) must obtain its OpenAI client from `resolve_openai_client()` (`sinan_agentic_core/llm/factory.py`) — the owned wrapper that reads back the client `configure_llm_provider(...)` installed via `set_default_openai_client(...)`, and builds a bare `AsyncOpenAI()` only when no provider has been configured. Do not construct a client at the call site, do not read provider keys, endpoints, or deployment names directly, and do not call `AsyncOpenAI(api_key=get_default_openai_key())`.

`resolve_openai_client()` is also the only place in the codebase allowed to import `agents.models._openai_shared` — `openai-agents==0.18.3` exports `set_default_openai_client` from the `agents` root but no matching getter, so reading the client back needs the private module. Confining that import to the module that already owns the setter side keeps the SDK-private surface at one site instead of one per call site (CLAUDE.md rule 5: consumers must not reach into `agents.*` internals). Re-check for a public getter when the SDK version bumps.

**Why:** Issue #35 — the recovery branch built `AsyncOpenAI(api_key=get_default_openai_key())`, bypassing the configured default. Under `AzureOpenAIProviderConfig`, `configure_llm_provider` (`sinan_agentic_core/llm/factory.py:42`) installs an `AsyncAzureOpenAI` via `set_default_openai_client(...)` but never sets a default key, so the rescue call crashed at client construction with `OpenAIError: The api_key client option must be set...`. Under plain OpenAI it masked itself whenever `OPENAI_API_KEY` was exported in the environment, which is why CI stayed green and the regression only surfaced on the first Azure-hosted evaluation. The framework's contract is that `configure_llm_provider` is the single point that owns provider-specific client wiring; any model-call site that rebuilds its own client breaks that contract.

**How to apply:** One call, at the top of the bypass branch:

```python
from ..llm import resolve_openai_client

client = resolve_openai_client()
```

Apply this on every new SDK-bypassing branch — current and future — including recovery, repair, summarize-and-extract, and any provider-specific escape hatch added later. Tests that need to inject a stub client patch the resolver at its import site (`patch("sinan_agentic_core.core.base_runner.resolve_openai_client")`), not `openai.AsyncOpenAI` — the branch no longer constructs a client, so patching the constructor injects nothing. Tests for the resolver itself patch `sinan_agentic_core.llm.factory.get_default_openai_client`.

## Run-level SDK kwarg wiring on every `Runner`-calling site in `sinan_agentic_core`

Every call site anywhere in `sinan_agentic_core/` that calls `Runner.run(...)`, `Runner.run_streamed(...)`, or builds `agent.as_tool(...)` kwargs must route each per-run SDK setting through its own `_build_*`/`build_*` helper and set the corresponding kwarg when the helper returns non-`None` — whether that call site is a branch inside `BaseAgentRunner` or a standalone function elsewhere in the package. The same discipline applies one level down: when a per-run setting is built by more than one `_build_run_config`-shaped or `_build_error_handlers`-shaped function (one per call-site family), adding that setting to one function does not add it to its siblings — each must be checked independently. Confirmed sites: issue #41's `self._build_run_config(agent_def)` → `run_config=` on all five `base_runner.py` branches (`_execute_basic` `:332`, `_execute_with_fallback` `:384`, `_execute_streamed` `:533`, the `as_tool` sub-agent branch `:780`, `run_agent()` `:699`); issue #42's `self._build_error_handlers(agent_def)` → `error_handlers=` on the four `Runner.run`/`Runner.run_streamed` branches (`_execute_basic` `:338`, `_execute_with_fallback` `:398`, `_execute_streamed` `:553`, `run_agent()` `:723`); issue #59's `build_run_config(resolved)` → `run_config=`, wired on all three `services/chat.py` functions (`chat()` `:137-139`, `chat_with_hooks()` `:214-216`, `chat_streamed()` `:298-300`) — call sites that are not `BaseAgentRunner` branches at all; issue #80's `tool_output_trim` setting, present in `BaseAgentRunner._build_run_config` (`base_runner.py:883-907`) but missing from the sibling `run_config.build_run_config()` (`run_config.py:37-66`) that `services/chat.py` calls — the same setting, wired on one `_build_run_config`-shaped function and not its sibling, rather than missing from a `Runner.run` call site entirely; and issue #89's `invalid_output_recovery` flag, read directly off `agent_def.invalid_output_recovery` in `BaseAgentRunner._build_error_handlers` (`base_runner.py:914-932`) but absent from the sibling `output_recovery.build_error_handlers(agent)` (`output_recovery.py:175-201`) that `services/chat.py`'s three functions and any direct `Runner.run()` caller use — the same sibling-function gap as issue #80, this time on the `error_handlers`-building pair instead of the `run_config`-building pair.

When adding a new execution branch, a new `_build_*`/`build_*` helper for a new per-run SDK setting, or a new module anywhere in `sinan_agentic_core/` that calls `Runner.run`/`Runner.run_streamed`/`as_tool`, confirm the setting reaches every such call site in the package — not just the ones under active development, and not just the ones inside `base_runner.py`. Also confirm it reaches every other function that assembles a `RunConfig`/`error_handlers` for a different call-site family (currently `BaseAgentRunner._build_run_config` / `run_config.build_run_config`, and `BaseAgentRunner._build_error_handlers` / `output_recovery.build_error_handlers` — check both members of a pair when either changes). A branch marked deprecated or "kept for backward compatibility" is not exempt: it still calls the SDK and still needs the setting, or its outputs silently diverge from the other branches.

**Exception — genuine SDK gaps, not oversights:** a call site is not in violation if the underlying SDK call does not accept the kwarg for that call shape. Verify this against the installed SDK version — do not assume — then document the gap inline with a `NOTE:` comment at the call site naming the SDK method and version checked, so a future reviewer (or `/check-code-quality`) can tell a real limitation apart from a missed wiring site. Issue #42: `Agent.as_tool()` accepts `run_config` (wired at `:804-806`) but has no `error_handlers` parameter in `openai-agents==0.18.3`, so the `as_tool` branch is correctly left out of `_build_error_handlers` wiring, documented at `base_runner.py:808-811`. Re-check when the SDK version bumps.

**Why:** Issue #41 — `_build_run_config` (pre-approval for tool-input guardrails) was wired onto `_execute_basic`, `_execute_with_fallback`, `_execute_streamed`, and the `as_tool` branch, but `run_agent()` — kept only for backward compatibility — was left out on the first pass. `check-code-quality` failed twice citing the identical gap (`run_agent() ... without run_config wiring`) before a third pass wired it. Issue #42 is a second, independent instance of the same class: a new helper (`_build_error_handlers`) needed the identical per-branch wiring, and this time landed correctly on the first pass — but its one skipped branch (`as_tool`) needed to be told apart from a repeat of the #41 gap. Issue #59 is a third instance, one level up: the identical per-run setting (tool-input pre-approval) needed the identical wiring discipline on `services/chat.py`'s three functions, which are not `BaseAgentRunner` branches — a call site family this rule's wording did not previously name. It landed correctly on the first pass by reusing the extracted `build_run_config()` helper, but a rule worded exclusively around `base_runner.py` risks a future contributor concluding that a new `Runner`-calling module elsewhere in the package is exempt, since it is not a "branch in `BaseAgentRunner`". Issue #80 is a fourth instance, and a narrower failure mode within the same class: `BaseAgentRunner._build_run_config` already resolved `tool_output_trim` via `_build_tool_output_trimmer`, but the standalone `run_config.build_run_config()` — the exact helper issue #59 wired into `services/chat.py` — had no equivalent branch, so an agent resolved through `chat()`/`chat_with_hooks()`/`chat_streamed()` ran untrimmed while the identical agent run through `BaseAgentRunner` was trimmed. The drift was not a missing call site (the call site was already correct) but a second `_build_run_config`-shaped function that lagged behind its sibling on a setting the first already had. The fix extracted the SDK-filter translation into a shared `build_tool_output_trimmer()` (`core/tool_output_trim.py:84-102`), imported by both functions, so future settings added to one route through the same shared translator rather than being reimplemented — but the wiring decision (which `config_kwargs` key each function sets) still lives separately in each function and still needs checking by hand. Issue #89 is a fifth instance, the same narrower failure mode as #80 but on the `error_handlers`-building pair instead of the `run_config`-building pair: `BaseAgentRunner._build_error_handlers` already read `invalid_output_recovery` off `agent_def` on every execution branch, but the standalone `output_recovery.build_error_handlers(agent)` that `services/chat.py` and any direct `Runner.run()` caller use had no equivalent check, so an agent declaring `invalid_output_recovery: false` failed loudly under `BaseAgentRunner` and was silently recovered under `chat()`. Because the standalone function only holds a built `Agent`, not the `agent_def` its sibling has, the fix resolved the flag by looking the definition up through `get_agent_registry().get(agent.name)` — the same by-name pattern issue #80 established for `_declared_tool_output_trim` in `run_config.py:93-104` — rather than inventing a second mechanism. This is now the fifth distinct per-call-site concern to require this discipline — see the capability-hook and client-reuse entries above in this file — because the class spans multiple near-duplicate `Runner`-calling sites and multiple near-duplicate `RunConfig`/`error_handlers`-building functions, with no shared mechanism that enforces a new per-run setting reaches all of them. Issue #93 closed the gap in the by-name lookup itself: once two sibling functions (`_declared_tool_output_trim`, `_recovery_opted_out`) each called the identical `get_agent_registry().get(agent.name)` inline, the lookup was extracted into `resolve_agent_definition()` (`registry/agent_registry.py:90-109`), and both callers now route through it instead of repeating the raw call — the same "second caller earns an extraction" discipline as the translator-placement rule below, applied to a registry lookup instead of a Pydantic-to-SDK translation.

**How to apply:** Use the pattern at `base_runner.py:332-334` (`_execute_basic`, `_build_run_config`), `:338-344` (`_build_error_handlers`), or `services/chat.py:137-139` (`chat()`, `build_run_config`): `<setting> = self._build_<setting>(agent_def)` (or `build_<setting>(agent)` outside `BaseAgentRunner`); `if <setting> is not None: run_kwargs["<kwarg>"] = <setting>`, placed before the `Runner.run(**run_kwargs)` / `Runner.run_streamed(**run_kwargs)` / `tool_agent.as_tool(**as_tool_kwargs)` call. Before shipping any new `_build_*`/`build_*` helper or per-run SDK setting, grep the whole package — `grep -rn 'Runner\.run(\|Runner\.run_streamed(\|as_tool_kwargs' sinan_agentic_core/` — not just `base_runner.py`. Every hit must either carry the new kwarg or a `NOTE:` comment citing the specific SDK method/version that lacks the parameter. Additionally, when a new setting is added to one member of a sibling pair — `BaseAgentRunner._build_run_config` / `run_config.build_run_config`, or `BaseAgentRunner._build_error_handlers` / `output_recovery.build_error_handlers` — check the other by name (`grep -rn 'def build_run_config\|def _build_run_config\|def build_error_handlers\|def _build_error_handlers' sinan_agentic_core/core/`) and confirm both resolve the same settings. A standalone sibling that only receives a built `Agent` (not the `agent_def` its `BaseAgentRunner` counterpart holds) resolves definition-level settings via `resolve_agent_definition()` (`registry/agent_registry.py:90-109`) — see `_declared_tool_output_trim` (`run_config.py:93-106`) and `_recovery_opted_out` (`output_recovery.py:217-230`) — not by inventing a new lookup path per setting, and not by calling `get_agent_registry().get(agent.name)` inline: that duplicate is exactly the pattern `resolve_agent_definition()` replaced (issue #93). If a new by-name reader appears at a third call site, extend `resolve_agent_definition()`'s callers rather than writing a second inline lookup. Extract any new SDK-translation logic into a shared function in the relevant `core/*.py` module (e.g. `core/tool_output_trim.py`) so both call it instead of each reimplementing it.

## Translate a declared config into SDK settings via a module-level function beside the Pydantic model, not a private `BaseAgentRunner` method

Every `core/*.py` module that defines a Pydantic model translating a YAML-declared setting into an `agents.*` SDK object — `model_retry.py`'s `ModelRetryConfig`, `tool_output_trim.py`'s `ToolOutputTrimConfig`, `turn_budget.py`'s `TurnBudgetConfig`, and `tool_error_recovery.py`'s `ToolErrorRecoveryConfig` — must expose that translation as a module-level `build_*` function declared beside the model, not as a private method on `BaseAgentRunner`. When a second caller — an overlay helper in the same module, a different execution branch, an SDK-bypassing runner branch — needs the same translated object, it imports the module-level function; it does not gain its own `_build_*` method on `BaseAgentRunner` that reimplements the same `if config is None: return None` / `.build()` (or equivalent) check inline.

This is narrower than the run-level SDK kwarg wiring rule above: that rule governs whether a *per-run setting* reaches every `Runner.run`-calling site; this one governs where the *single-value translation* for one config model lives once a second caller needs it. A `_build_*` method that only assembles several already-translated values into one kwarg bundle (`_build_run_config`, `_build_error_handlers`) is not in scope here — only a method that duplicates a config model's own `is None` / `.build()` translation is.

**Why:** Issue #80 first established this shape: `build_tool_output_trimmer()` (`core/tool_output_trim.py:84`) is the shared translator both `BaseAgentRunner._build_run_config` and the standalone `run_config.build_run_config()` call. Issue #90 repeated the same fix one config module over: `BaseAgentRunner._build_model_retry()` reimplemented the identical `if agent_def.model_retry is None: return None; return agent_def.model_retry.build()` check that `model_retry.apply_model_retry()` already performed inline — one check, written twice, because the SDK-bypassing overflow-fallback branch inside `_execute_with_fallback` needed the translated settings and had no shared place to get them from except its own private method. The fix in both cases was identical: extract the translation into a module-level function beside the config's Pydantic model (`build_model_retry_settings()`, `core/model_retry.py:116`), delete the runner's private duplicate, and have every caller — the overlay function and the bypass branch alike — import the shared function instead. Issue #96 is a third instance, and it widens the class: the two hand-written translations were not a `BaseAgentRunner` method duplicating a config module's own check, but two registry-layer callers duplicating it instead — `AgentYamlEntry.build_turn_budget()` (`registry/agent_catalog.py`, the `turn_budget:` shorthand) and `capability_registry._build_turn_budget()` (the explicit `capabilities:` list), each hand-assembling a `TurnBudget` field by field from `TurnBudgetConfig`. The fix was the same shape again: `TurnBudgetConfig.build()` (`core/turn_budget.py:276`) forwards `model_dump()` wholesale so a new field needs no second edit, and the module-level `build_turn_budget()` (`core/turn_budget.py:292`) carries the shorthand path's "off unless declared" check so neither registry caller reimplements it. Issue #97 completed the fourth instance, closing out the sweep this rule tracked as pending: `tool_error_recovery.py` gained `ToolErrorRecoveryConfig.build()` (`core/tool_error_recovery.py:463`) and the module-level `build_tool_error_recovery()` (`core/tool_error_recovery.py:485`), which folds in the "off when disabled" rule the boolean paths need. Every declaration path routes through it — the `error_recovery:` shorthand (`AgentYamlEntry.build_error_recovery()`, `registry/agent_catalog.py`), the explicit `capabilities:` list entry (`capability_registry._build_error_recovery()`), and, unlike the three prior instances, a third caller from the outset: the `error_recovery=` bool kwarg on `BaseAgentRunner.execute()` (`core/base_runner.py:249-250`), which previously hand-wrote its own `if error_recovery is True: ... elif error_recovery is False: ...` inline instead of importing a shared translator, because no shared translator existed yet for this config. All four declarative SDK-config modules (`model_retry.py`, `tool_output_trim.py`, `turn_budget.py`, `tool_error_recovery.py`) now carry this treatment.

**How to apply:** Before adding a private `_build_*` method or a second hand-written translation anywhere — on `BaseAgentRunner` or on a sibling registry-layer function — that reimplements a `core/*.py` Pydantic config's own translation into an SDK object, check whether the config module already exposes, or should expose, a module-level `build_*` function for that translation; see `build_model_retry_settings()` (`core/model_retry.py:116`), `build_tool_output_trimmer()` (`core/tool_output_trim.py:84`), `build_turn_budget()` (`core/turn_budget.py:292`), and `build_tool_error_recovery()` (`core/tool_error_recovery.py:485`) for the pattern. If it does not exist yet, add it there instead of at the call site. Keep it unexported from `core/__init__.py` while every caller stays in-package, matching all four current instances. The function's parameter is the config value itself (`retry: ModelRetryConfig | None`, `turn_budget: TurnBudgetConfig | None`, `enabled: bool` for the boolean-declaration case), not the enclosing `agent_def` — a signature narrower than a runner or registry private method, so callers that only have the config value can use it directly. This applies whenever a second (or third) caller needs a translation that already exists somewhere as inline logic, not only when authoring a brand-new config module and not only when that caller is a `BaseAgentRunner` method — a direct SDK-bypassing kwarg path (like `execute()`'s `error_recovery=` bool) counts as a caller too, per issue #97.

## Rebuild a capability's `clone()` from its declared config model, not a hand-written field list

Any `Capability` (or similarly declaratively-configured runtime object) in `sinan_agentic_core/core/` that has a matching Pydantic config model — `ToolErrorRecoveryConfig`, `TurnBudgetConfig` — must rebuild itself in `clone()` by reading every field the config model declares back off `self` via `<Config>.model_fields` and forwarding them wholesale into the constructor, not by naming each field individually. This requires every config field to be stored on the instance as a public attribute of the *same name* as the field — a private or renamed attribute (`_mcp_hints` for a `mcp_hints` field) has nothing for the reflection to read under the field's name. Live, non-declarable references the constructor also needs (a `tool_registry`, an open connection) are passed as separate explicit kwargs, outside the reflected field set — mirroring how `build()` already treats them in the declaration-to-runtime direction (see the translator rule above).

**Why:** Issue #103 — `ToolErrorRecovery.clone()` (`core/tool_error_recovery.py:283`) named its three fields by hand (`tool_registry=self._registry, mcp_hints=dict(self._mcp_hints), max_identical_before_stop=self.max_identical_before_stop`), the same drop-on-clone hazard `ToolErrorRecoveryConfig.build()` (`core/tool_error_recovery.py:475`) once had in the opposite direction before issue #97 fixed it there. A field added to `ToolErrorRecoveryConfig` would silently not reach clones until `clone()` was edited a second time. The fix renamed the private `_mcp_hints` to a public `mcp_hints` attribute so its name matched the config field, then rewrote `clone()` as `declared = {name: getattr(self, name) for name in ToolErrorRecoveryConfig.model_fields}; return ToolErrorRecovery(tool_registry=self._registry, **declared)`. The same issue's thread cites two sibling instances of the identical shape, not yet fixed: `TurnBudget.clone()` (`core/turn_budget.py:213-221`) names all five of `TurnBudgetConfig`'s fields by hand, and `ToolTracer.clone()` (`core/tool_tracer.py:107-114`) names all four of its fields by hand — though `ToolTracer` has no matching config model yet, so it needs the attribute-name contract established first, not just the reflection.

**How to apply:** Before writing or reviewing a `clone()` method on a `core/*.py` capability that has a `*Config` Pydantic model, confirm every config field is stored as a same-named public instance attribute; rename any private or mismatched one first. Then rebuild `clone()` as `declared = {name: getattr(self, name) for name in <Config>.model_fields}` and forward it into the constructor via `**declared`, passing any live non-config reference as a separate explicit kwarg rather than folding it into the reflected set. Do not route `clone()` through the config's `build()` method instead of the constructor directly — `build()` may fall back to a process-wide default (e.g. the global tool registry) when a value is absent, which would silently give a clone a default its original never had; pin this with a test asserting a registryless original stays registryless after `clone()` (see `test_a_clone_of_a_registryless_tracker_stays_registryless`, `tests/test_tool_error_recovery.py`). Add a test that every field in `<Config>.model_fields` round-trips from original to clone (`test_clone_carries_every_declared_field`, same file). `TurnBudget.clone()` (`core/turn_budget.py:213`) is the next confirmed pending site — it already has `TurnBudgetConfig` to reflect over. `ToolTracer.clone()` (`core/tool_tracer.py:107`) has no config model yet; establishing one there is a prerequisite this rule does not cover by itself.

## Verify claims about a wrapped SDK object's behavior before asserting them in a validator or doc

Any `Field` constraint, `model_validator`, error message, docstring, or README paragraph that asserts what a wrapped `agents.*` object does or does not do with a given input must be checked against the installed SDK's actual behavior — read its source or drive the real object through a representative input — before being written. Do not derive the claim from how the object's name or parameters suggest it "should" behave.

**Why:** Issue #46 — `ToolOutputTrimConfig` (`sinan_agentic_core/core/tool_output_trim.py`) added a cross-field validator rejecting any policy where `preview_chars >= max_output_chars`, on the premise that such a preview "never shortens an output." The premise was never checked against `agents.extensions.ToolOutputTrimmer`: the SDK compares the assembled replacement's length to the *original tool output's* length, not to `max_output_chars`, so `preview_chars == max_output_chars == 500` still collapsed a 100,000-character output to 566 characters. The same false premise was written four times — the validator's error message, its docstring, `README.md`, and a test docstring — before a reviewer measured the real filter against the installed SDK and found the rejected configuration was one of the most natural policies to express (`preview_chars: 500` with `max_output_chars: 500`, "keep the first 500 characters of anything bigger"). The wrapper ended up more restrictive than the library it wraps, on a claim that did not hold, and the same unverified claim was carried into three more artifacts before anyone tested it.

Issue #69 repeated the same shape one level up, in a usage-example comment rather than a validator: `README.md`'s `chat_streamed` example for a `model_refusal` payload showed `{"error": "I can't help with that."}`, but `ModelRefusalError` renders as `Model refused to produce output: <refusal>` (verified against `openai-agents==0.18.3`, `agents/exceptions.py`). Nobody had checked the exact rendered text against the installed SDK before writing it into the doc — the same unverified claim as issue #46, just in a top-level README example instead of a `core/` config validator.

**How to apply:** Before adding a validator, `Field` constraint, docstring, or doc paragraph in `sinan_agentic_core/core/` that says a wrapped SDK object "always," "never," or "would never" does something with valid input, drive the installed object through that input in a throwaway script or a test and read the actual result. This applies to every module that translates a YAML-declared config into an SDK class — `tool_output_trim.py`, `model_retry.py`, `tool_error_recovery.py`, and future siblings — whenever the config layer adds a constraint the SDK class itself does not enforce. This is the same discipline as the SDK-version-gap exception in the entry above, applied to behavior instead of parameter presence: verify against the installed package first, then write the claim once it is confirmed true.

The same check applies outside `core/` and outside validators: any doc paragraph, docstring, or usage-example comment anywhere in the repo — `README.md` included — that shows the literal string a wrapped `agents.*` exception or object renders must be verified against the installed SDK version before being committed. See `core/run_errors.py`'s `run_error_payload()`, whose `error` value is `str(error)` on whatever the SDK raised, and the README's `chat_streamed` `model_refusal` example it feeds, for the pattern: render the real exception through the installed package, then quote that text exactly rather than a plausible-sounding guess.

## Parse a fully-defaulted optional YAML config block with `is not None`, never a truthiness check

Any code in `sinan_agentic_core/registry/` that builds a Pydantic model from an optional block in `agents.yaml`/`tools.yaml` — where the model itself has no required fields — must guard on `block is None`, not `if block:`/`if block else None`. Route it through `_parse_optional_block()` (`sinan_agentic_core/registry/agent_catalog.py:268-283`) rather than reimplementing the check inline. Where the block is already declared as an optional model field on the catalog's resolved entry — `ToolYamlEntry.mcp: ToolMCPConfig | None` (`sinan_agentic_core/registry/tool_catalog.py:59`) — read it off the resolved entry (`self.get(name).mcp`) instead of re-parsing the raw dict: the field declaration already applies the rule, and going through it also validates the block's own fields. An empty mapping (`{}`) is a valid declaration meaning "enable this with the model's defaults"; a truthiness check treats it as absent, which is a different, wrong behavior for a model that has no required fields.

**Why:** Issue #66 — `AgentCatalog.get()` parsed three optional blocks off the same raw agent entry. `tool_output_trim` correctly guarded on `raw_trim is not None`; the two siblings four lines above, `turn_budget` and `model_retry`, guarded on plain truthiness (`if raw_budget else None`), so `turn_budget: {}` / `model_retry: {}` silently opted an agent *out* of a feature its author had just written to opt it *into* — both `TurnBudgetConfig` and `ModelRetryConfig` are fully defaulted, so the empty mapping is a meaningful declaration, not an absence. The correct rule already existed once in the same function; writing it three separate times let two of the three drift from it. The fix collapsed all three call sites into one `_parse_optional_block()` helper so the rule exists once, not per call site.

Issue #81 is the same shape in the sibling catalog: `ToolCatalog.get_mcp_tools()` read the `mcp` block off the raw dict as `if mcp_raw and mcp_raw.get("expose", False)`, even though `ToolYamlEntry.mcp` four lines up already declares that block as `ToolMCPConfig | None`. Because `ToolMCPConfig.expose` defaults to `False`, the empty-mapping case produced the same list either way — but the inline read bypassed the model, so `expose` was tested for truthiness rather than validated: `expose: "no"` exposed a tool its author had turned off, and `expose: "maybe"` exposed it silently instead of raising. The fix deleted the raw read and resolved through `self.get(name).mcp`, which removed the last inline copy of the rule in `registry/`.

**How to apply:** When adding a new fully-defaulted optional config block anywhere `AgentCatalog` or `ToolCatalog` parse `agents.yaml`/`tools.yaml`, call `_parse_optional_block(raw, key, Model)` instead of writing a new inline `raw.get(key)` plus truthy check — or, when the catalog's resolved entry already declares the block as an optional model field, read it from that entry and drop the raw-dict access entirely. Do not extend this to a block collected as a *list or set of members* rather than validated as a single model — `capabilities` and `tool_rules` genuinely mean "nothing declared" when empty, not "opt in with defaults." The rule applies only when an empty mapping and the model's own defaults express the same declaration. Before shipping a change in `registry/`, `grep -rn 'raw\.get(\|_raw_tools\[\|_raw_agents\[' sinan_agentic_core/registry/` and confirm no optional single-model block is read for truthiness outside `_parse_optional_block()` or a resolved entry's field.

## Forward the whole raw block when a Pydantic model gates on `extra="forbid"`

Any Pydantic model in `sinan_agentic_core/registry/` or `sinan_agentic_core/mcp/` that declares `model_config = ConfigDict(extra="forbid")` to reject an unrecognized YAML key is only a real gate if its call site constructs it from the raw block itself — `Model(**raw)`, or `dict(raw)` updated with only the fields that need transformation before being splatted in, as `AgentCatalog.get_mcp_server()` (`registry/agent_catalog.py:386-392`) does for `MCPServerConfig` (`mcp/yaml_schema.py:87`). If the call site instead hand-picks fields into named keyword arguments — `Model(field=raw.get("field"), ...)` — an unrecognized key is dropped by the hand-picking code before the model ever sees it, so `extra="forbid"` gates nothing and a typo is silently accepted exactly as before the setting was added.

**Why:** Issue #98's sweep added `extra="forbid"` across every YAML-parsed config model. `MCPServerConfig` needed a two-part fix, not one: `get_mcp_server()` previously built it from hand-picked keys (`resources=[MCPResourceConfig(**r) for r in raw.get("resources", [])]`, `description=raw.get("description", "")`, etc.), so adding `extra="forbid"` to the model alone would have gated nothing — the fix also rewrote the call site to forward `dict(raw)` with only `name`/`tools`/`write_tools` resolved. The same sweep deliberately left two sibling models untouched for the identical reason: `AgentYamlEntry` (`registry/agent_catalog.py:73`) is still built field-by-field in `AgentCatalog.get()` (`registry/agent_catalog.py:318-333`), and `CapabilityRef` (`registry/agent_catalog.py:58`) is still built as `CapabilityRef(name=item["name"], config=item.get("config", {}) or {})` in `_parse_capabilities()` (`registry/agent_catalog.py:230`) — a mistyped key in either an agent entry or a `capabilities:` list item is dropped by the hand-picking code, not the model, so declaring `extra="forbid"` on either without first rewriting its call site would be a no-op safety net.

**How to apply:** Before adding `model_config = ConfigDict(extra="forbid")` to a model in `registry/` or `mcp/`, `grep -rn "<ModelName>(" sinan_agentic_core/` and inspect every construction site. If a site builds the model from explicit `field=raw.get(...)` kwargs rather than forwarding the raw dict, fix the call site first — mirror `get_mcp_server()`'s `resolved = dict(raw); resolved.update(name=..., tools=..., write_tools=...); Model(**resolved)` shape, resolving only the fields that need transformation — then add the `model_config`. Adding the setting without the call-site fix is not a partial improvement; it changes nothing observable and should not be treated as complete. `AgentYamlEntry` and `CapabilityRef` are the two confirmed pending sites: both need their call site (`AgentCatalog.get()`, `_parse_capabilities()`) rewritten to forward the raw entry before `extra="forbid"` would reject anything on them.

## Read a Registry through its own public accessors, never its private dict

Code outside `sinan_agentic_core/registry/` must not read a `Registry` class's leading-underscore attribute (`ToolRegistry._tools`, `AgentRegistry._agents`, `GuardrailRegistry._guardrails`) directly. If an existing public accessor covers the need (`get`, `get_all_functions`, `get_tool_functions`, `list_names`, `list_all`), call it. If none fits, add the accessor to the registry class itself — in `sinan_agentic_core/registry/` — rather than reaching past it. Do not add an accessor with no caller; add exactly the one the call site needs.

**Why:** Issue #58 — `BaseAgentRunner.__init__` built `tool_map` by comprehending over `self.tool_registry._tools.items()` (`base_runner.py:75`), and `_build_tools()`/`_build_handoffs()` checked membership and fetched definitions via `self.agent_registry._agents` at three more sites (`:821`, prior duplicate lookup, and `:980`), instead of the registry's own `.get()`. All four were the last sites in a repo-wide sweep tracked from epic #39 through #41: after the fix, `ToolRegistry` gained `get_all_functions()` (mirroring the pre-existing `GuardrailRegistry.get_all_functions()`), and both call sites in `base_runner.py` switched to `AgentRegistry.get(name)`. A grep across `sinan_agentic_core/` and `examples/` after the fix found zero remaining `_tools`/`_agents`/`_guardrails` reads outside the registry modules that own them — confirming the class of mistake, not a one-off.

**How to apply:** Before writing new code in `sinan_agentic_core/core/`, `sinan_agentic_core/registry/agent_factory.py`, or `examples/` that inspects a `ToolRegistry`, `AgentRegistry`, or `GuardrailRegistry` instance, check for an existing public accessor first — see `ToolRegistry.get_all_functions()` (`registry/tool_registry.py:60-62`) and `AgentRegistry.get()` (`registry/agent_registry.py:65-67`) for the pattern each new accessor should follow. This rule applies only to this codebase's own `Registry` classes — it does not cover third-party objects (e.g. the MCP SDK's `server._tool_manager._tools`, tracked separately under the SDK-internals sweep). Before shipping, `grep -rn '\._tools\b\|\._agents\b\|\._guardrails\b' sinan_agentic_core/ examples/` and confirm every hit is inside `sinan_agentic_core/registry/`.

## Access a third-party SDK object through its public API, never a leading-underscore attribute

Code anywhere in this repo — tests included — that reads an attribute or calls a method on an object owned by a third-party package (`mcp.server.fastmcp.FastMCP`, `agents.*`, or any future SDK dependency) must not touch a name starting with `_` on that object. Check the SDK's public surface first — a listing method, a getter, a documented accessor that returns the same information a real client of that SDK would see. If a public equivalent exists, use it even when it costs an `await` or a slightly less direct read. If no public equivalent exists, the private read is unavoidable, but confine it to exactly one function or module that owns the exception and document why inline — do not repeat the private import or attribute read at every call site that needs the value.

**Why:** Issue #75 — six sites across `tests/test_mcp/test_server_builder.py` (`:112,131,149,165,187,204,224`) read `server._tool_manager._tools` and called a tool's handler via `discover_tool.fn(...)` directly, coupling the tests to the MCP SDK's internal `ToolManager` layout instead of the public contract an actual MCP client uses. Both had public equivalents on `mcp==1.27.0` (`await server.list_tools()`, `await server.call_tool(name, args)`), so the fix replaced every private read outright; a repo-wide `grep -rn '_tool_manager\|_resource_manager\|_prompt_manager'` confirmed zero remaining sites. Issue #74 is the adjacent case where no public equivalent existed: `resolve_openai_client()` (`sinan_agentic_core/llm/factory.py:25`) needs to read back the client `set_default_openai_client(...)` installed, but `openai-agents==0.18.3` exports the setter with no matching public getter, so reading it back required importing the private `agents.models._openai_shared` module. That fix did not avoid the private import — it isolated it to the one wrapper function every caller routes through, instead of importing the private module at each call site. The Registry-internals rule above already flagged this repo's own `Registry` classes as a distinct, narrower case and pointed at "the SDK-internals sweep" as a separate concern — this entry is that sweep's rule.

**How to apply:** Before writing test or production code that reads a `_`-prefixed attribute or calls a `_`-prefixed method on a third-party object, check the SDK's public API (its documented methods, or its `__all__`/exported symbols — not a guess) for an equivalent. Prefer the public call even in tests, mapping return values into the shape the test needs (see `listed_tools()`, `tests/test_mcp/test_server_builder.py`, which maps `await server.list_tools()` by name). If genuinely no public equivalent exists, confine the private read to one owned wrapper — see `resolve_openai_client()`, `sinan_agentic_core/llm/factory.py` — and have every other call site import the wrapper, not the private SDK symbol. Before shipping a change that touches a third-party SDK object, `grep -rn '\._tool_manager\|\._resource_manager\|\._prompt_manager\|agents\.models\._openai_shared\|agents\._'` (extend the pattern for any newly adopted SDK) across the changed files and confirm no sibling private-access site was missed.

## Share literal formatting logic between `BaseAgentRunner._execute_streamed` and `chat_streamed`'s streamed event dicts

Both `BaseAgentRunner._execute_streamed` (`sinan_agentic_core/core/base_runner.py`) and `chat_streamed` (`sinan_agentic_core/services/chat.py`) build the same shaped event dicts — `tool_output`, `tool_call`, `message_output`, `agent_updated` — off the same SDK stream items, independently, one copy per function. Any literal, cutoff length, or rendering decision embedded in one of those dicts must live in exactly one shared function in `core/`, imported by both, not written inline in each function.

**Why:** Issue #102 — both functions independently truncated a tool's output to `str(item.output)[:500]` when building the `tool_output` event: the identical `500` was one decision, written twice, with nothing stopping the two copies from drifting to different lengths. The fix extracted `tool_output_preview()` / `TOOL_OUTPUT_PREVIEW_CHARS` into a new `core/stream_preview.py`, imported by both call sites. The other three event dicts these two functions build (`tool_call`, `message_output`, `agent_updated`) still assemble their shape as separate literal copies in each function — the same duplication, just not yet forced to visibly drift by an inline literal, and therefore not yet caught.

**How to apply:** Before adding or changing a literal, cutoff, or format string embedded in a streamed event dict inside `_execute_streamed` or `chat_streamed`, check whether the sibling function computes the equivalent value. If so, extract a shared function into `core/` (see `tool_output_preview()`, `core/stream_preview.py`) rather than editing the value in only one of the two. ## Name a default value once, in a module-level constant, when it is repeated across a capability's runtime dataclass and its declared config counterpart

Any `core/*.py` module that pairs a runtime `Capability` (or similarly runtime-facing dataclass) with a declared Pydantic config model — `TurnBudget` / `TurnBudgetConfig`, and the analogous entry-model / raw-dict-fallback / runtime-definition triples in `registry/agent_catalog.py`, `registry/agent_registry.py`, and `core/base_runner.py` — must define each value the two sides share exactly once, as a module-level `UPPER_SNAKE_CASE` constant beside the class that owns the concept, and have every field declaration that repeats it read from that constant rather than restating the literal.

**Why:** Issue #105 — a propagation-umbrella scan (`new_pattern:shared-default-constant`, first named by issue #2517) found this pattern recurring: `TurnBudget`'s dataclass field defaults were the literal `10`/`2`/`3`/`5` a second time in `TurnBudgetConfig`'s Pydantic field defaults, with nothing forcing the two lists to stay in sync if one changed. **How to apply:** Before adding or reviewing a field with a default value on a `core/*.py` runtime dataclass or `Capability`, check whether a paired Pydantic config model, entry model, or raw-dict fallback declares the same value. Add a parity test that reflects over the config model's `model_fields` and compares each default against a default-constructed instance of the runtime class, matching `test_the_declared_defaults_match_the_runtime_defaults`, so a field added to one side without the other fails loudly rather than silently drifting. The three sites cited above (`registry/agent_catalog.py`, `core/base_runner.py` twice) are confirmed pending under this same class — apply the identical fix when picked up, rather than treating each as a one-off literal.

## Resolve compound JSON-schema/annotation shapes recursively in `tool_adapter.py`, never off a flat top-level lookup

Any function in `sinan_agentic_core/mcp/tool_adapter.py` that translates between a JSON-schema property and a Python type annotation — in either direction — must resolve compound shapes recursively: fold `anyOf` branches (treating a `{"type": "null"}` branch as nullability), recurse into `items` for arrays, and recognize parameterized/union Python annotations (`list[T]`, `dict[K, V]`, `T | None`). It must not key off a single top-level `type` (or bare annotation) read against a flat scalar dict and silently fall back to a default on a miss.

**Why:** Issue #50 — `_build_mcp_handler` read `prop_def.get("type", "string")` to map a JSON-schema property to a Python annotation. The OpenAI Agents SDK's strict schema expresses `list[str] | None` as `{"anyOf": [{"type": "array", "items": {"type": "string"}}, {"type": "null"}]}`, with no top-level `type` key; the lookup silently fell back to `"string"`, and because the SDK's strict schema also lists every property in `required` regardless of nullability, the parameter was advertised to MCP clients as a required `str`. `items` was discarded the same way even when `type: array` did match, so a required `list[int]` collapsed to a bare `list`. The fix, `_resolve_annotation()` (`tool_adapter.py:96-130`), replaced the flat lookup with recursive resolution. The sibling direction of the same translation, `_get_params_schema`'s raw-function path (`tool_adapter.py:48-81`), carries the identical shape unfixed: `type_map.get(annotation, "string")` (`:71`) keys off the bare Python type object, so a raw function declaring `tags: list[str] | None = None` builds a schema with `type: "array"` and no `items`, and `X | None` (a `types.UnionType`, not a key `type_map` contains) falls back to `"string"` — the mirror-image bug, tracked separately as issue #51, which landed the same recursive treatment on `_get_params_schema`'s raw-function path.

Issue #52 closed the test debt the prior paragraph left as a citation rather than a guarantee: the fix, tests only asserting `test_resolve_annotation`/`test_container_params_keep_their_type`, still asserted a resolved *handler signature* (`inspect.signature(handler)`), one layer short of what an MCP client actually receives. `test_server_builder.py` builds a real `FastMCP` server and calls `list_tools()`, and the new `test_the_advertised_schema_matches_the_one_the_sdk_produced` diffs the advertised `inputSchema` against the SDK's own `params_json_schema` — a check that would have caught a correct `_resolve_annotation()` output that FastMCP itself then rendered wrong, which no signature-level assertion can see. The same issue widened the parametrized matrix in `test_tool_adapter.py` to run every container case (`list[str]`, `list[int]`, `dict[str, Any]`, nested `list[list[str]]`, each required and optional) against all three entry points a tool can be registered through — the `FunctionTool` path, its `strict_mode=False` sibling (the only path that can carry `dict[str, Any]`, since the SDK's strict schema forbids the `additionalProperties` key an open mapping needs), and the raw-function path — so a fix landing on one entry point cannot ship while a sibling entry point regresses unnoticed.

**How to apply:** Before adding or reviewing a schema-to-annotation or annotation-to-schema translation in `tool_adapter.py`, check whether the input can be a parameterized or union shape, not just a bare scalar. On the JSON-schema-to-Python side, route through `_resolve_annotation()` (`tool_adapter.py:146`) rather than a new flat `dict.get("type", ...)` lookup. On the Python-annotation-to-JSON-schema side (`_get_params_schema`'s raw-function path, `tool_adapter.py:48-81`), a bare `type_map.get(annotation, "string")` needs the mirrored recursive treatment — inspect `typing.get_origin()`/`get_args()` for `list[T]`, `dict[K, V]`, and `T | None` before falling back to the scalar map. Pin both directions with parametrized tests covering optional and required `list[str]`, `list[int]`, `dict`, and a nested container, matching `test_resolve_annotation` and `test_container_params_keep_their_type` (`tests/test_mcp/test_tool_adapter.py`) — run the matrix against every entry point a tool can be registered through (`FunctionTool`, its `strict_mode=False` sibling for `dict[str, Any]`, and the raw-function path), not only the one the change touched. A signature-level assertion proves the resolved annotation is correct; it says nothing about what FastMCP advertises to a real client. Whenever a change reaches `tool_adapter.py`, also assert through `build_mcp_server(...)` + `list_tools()`, comparing the advertised `inputSchema` to the SDK's `params_json_schema` — stripping `title`/`default`, which vary by presentation rather than type — and checking `required` excludes every nullable property, matching `test_the_advertised_schema_matches_the_one_the_sdk_produced` (`tests/test_mcp/test_server_builder.py`).

## Copy a caller-supplied mutable dict/list before storing it as an instance attribute

Any `__init__` in `sinan_agentic_core/` that accepts a `dict`/`list` parameter and retains it as an instance attribute for later reads — on a registry, catalog, capability, or hook bundle meant to be a fixed snapshot of what it was given, as opposed to an object that intentionally shares *live* working state with its caller — must store a copy, never the caller's own reference (`self.x = x`, `self.x = x or {}`). A flat container (`dict[str, str]`) only needs a shallow copy: `dict(param or {})` / `list(param or [])`. A container that nests another mutable value — `dict[str, list[str]]`, `dict[str, dict[str, Any]]` — needs `copy.deepcopy(param)` instead: a shallow copy only detaches the outer container, so an edit inside a nested list or dict still reaches the stored attribute.

**Why:** Issue #103 — `ToolErrorRecovery.__init__` (`core/tool_error_recovery.py:111,131`) stored `mcp_hints or {}` by reference; a caller keeping its dict and mutating it after construction would silently change which hints the tracker resolved, and two trackers built from the same dict would have shared one mapping. Issue #111 repeated the same shape at a sibling site named by that fix's own propagation scan: `StreamingRunHooks.__init__` (`services/hooks.py:56`) stored `tool_friendly_names or {}` the identical way. Both fixes were the identical one-line change (`dict(param or {})`), because both maps were flat (`dict[str, str]`) — a shallow copy was enough to detach them. Issue #112 widened the class: `AgentCatalog.__init__` (`registry/agent_catalog.py:311-314`) aliased all four of its constructor parameters — `tool_groups`, `raw_agents`, `knowledge`, `raw_mcp_servers`. Three of the four (`dict[str, list[str]]`, `dict[str, dict[str, Any]]` twice) nest a mutable value, so the flat `dict()` copy that fixed #103 and #111 would not have been enough here: a caller could still edit a nested tool-group list or agent block after construction and reach the catalog. The fix used `copy.deepcopy` for those three and reserved the shallow `dict()` copy for the one flat map (`knowledge`). A propagation scan on #112 confirmed the identical aliasing shape — flat or nested — recurring at four more constructor sites, tracked under epic #39 as the same `bugfix_shape` class: `core/base_runner.py`'s composite run hooks (#113), `registry/tool_catalog.py`'s `raw_tools` (#114), `session/agent_session.py`'s initial history (#115), `services/events.py`'s sources list (#116).

Issue #113 closed the first of those four: `_CompositeHooks.__init__` (`core/base_runner.py:1258-1259`) stored a `list[Capability]` by reference, so a caller that appended to its own list after handing it to `_build_hooks()` — or to the sub-agent `as_tool()` path's `_CompositeHooks(sub_caps)` — silently changed what a live hooks bundle dispatched to, and two bundles built from one list shared a dispatch set. `Capability` is not a nested `dict`/`list`, so this is the flat case: the fix was the same one-line `list(capabilities)` copy as #103 and #111, not a `deepcopy`. It also sharpened the existing "live, caller-shared working state" exception: the capability *objects themselves* (a `TurnBudget`, a recovery tracker) are deliberately left shared after the container copy, because the runner reads their live state back after the run — pinned by `test_the_capabilities_themselves_stay_shared_with_the_caller` (`tests/test_tool_error_recovery.py`). A shallow container copy already achieves this for a flat list: only the outer list is detached, its elements stay the same live objects. Issue #113's own propagation scan filed one further sibling site not previously named: `AgentDefinition` (`registry/agent_registry.py:15`) is a plain `@dataclass`, so its auto-generated `__init__` assigns `tools`/`guardrails`/`handoffs`/`hosted_tools`/`capabilities` straight from the constructor arguments with no copy at all; the fix belongs in `__post_init__` (`registry/agent_registry.py:51-54`), which today only validates `instructions` and does not yet re-assign the five list fields to copies (issue #117).

Issue #114 closed the second of those four with the nested `dict`/`dict` shape already covered above: `ToolCatalog.__init__` (`registry/tool_catalog.py:111`) aliased `raw_tools` (`dict[str, dict[str, Any]]`), each value nesting an `mcp` block and its `annotations`, and the fix was the same `copy.deepcopy` treatment `AgentCatalog` already received under #112 — no new nuance.

Issue #115 closed the third, and widened the class again: the aliased parameter was not a bare `dict`/`list` but a custom object — `ConversationHistory` — wrapping a nested `messages` list of dicts (a structured-output `content` is itself a further list of dicts, one level deeper again). `AgentSession.__init__` (`session/agent_session.py:101-103`) stored `initial_history or ConversationHistory()` by reference, so appending to the session reached the caller's object and two sessions seeded from one history shared a single message list. Two fixes were considered and rejected before the one that shipped: rebuilding a fresh `ConversationHistory` and copying only its `messages` list in was rejected because the class docstring documents subclassing `ConversationHistory` for persistence backends, and rebuilding the base type would silently downgrade a caller's subclass; a shallow `list(initial_history.messages)` copy was rejected because it would detach only the outer list, leaving both the per-message `dict` and the nested structured-output `content` list open to edits reaching the stored object. The fix was `copy.deepcopy(initial_history)` on the object itself, pinned by tests covering a later append to the caller's history, an edit inside a seeded message's `content` field, an edit inside a nested structured-output `content` list, and two sessions seeded from one history not sharing a message list (`TestAgentSessionCopiesTheCallersHistory`, `tests/test_session.py`).

Issue #116 closed the fourth of those four, and confirmed the dataclass nuance issue #113 first raised for `AgentDefinition`: `AnswerEvent` (`services/events.py:114`) is a `@dataclass` with no hand-written `__init__`, so the copy went into `__post_init__` (`services/events.py:128-142`) — `self.sources = list(self.sources)` — not into a constructor that does not exist. The fix placed the copy on the dataclass itself rather than only in the `StreamingHelper.emit_answer()` helper most callers go through, because the module and the package's exports both document constructing `AnswerEvent` directly and pushing it down a caller-owned transport; a copy scoped to the helper would have left that second, equally real ingest path aliased. `sources` is `list[Any]` of opaque caller values (identifiers, paths, whole documents) that a consumer matches back to its own objects by identity, so — unlike the nested-`dict` cases above — only the outer list needed detaching; the elements stay shared on purpose, the same split issue #113 drew for `_CompositeHooks`'s capability list. **How to apply:** Before adding or reviewing an `__init__` parameter typed `dict[...]`/`list[...]` (optional or required) that gets assigned to `self.<name>` and read back later, check the parameter's declared type for a nested mutable value. If every value inside is immutable, or is a mutable object meant to stay live and caller-shared (a flat `dict[str, str]`, or a `list[Capability]` whose elements carry per-run state) — a shallow copy is enough: `dict(<param> or {})` / `list(<param> or [])`, matching `ToolErrorRecovery.mcp_hints` (`core/tool_error_recovery.py:131`), `StreamingRunHooks`'s tool-name map (`services/hooks.py:56`), and `_CompositeHooks._capabilities` (`core/base_runner.py:1258-1259`). If the type nests a `list`/`dict` — `dict[str, list[str]]`, `dict[str, dict[str, Any]]` — use `copy.deepcopy(<param>)` instead, matching `AgentCatalog._tool_groups`/`_raw_agents`/`_raw_mcp_servers` (`registry/agent_catalog.py:311-314`) and `ToolCatalog._raw_tools` (`registry/tool_catalog.py:111`); a shallow copy on a nested type leaves the constructor's non-aliasing claim false. If the parameter is not a bare `dict`/`list` but a custom object that itself wraps a nested mutable container — a `ConversationHistory` wrapping a `messages` list of dicts — deep-copy the object itself (`copy.deepcopy(<param>)`), not just its inner container: rebuilding a fresh instance and copying the container in loses a caller's subclass, and copying only the inner list leaves values nested inside it open; see `AgentSession.__init__` (`session/agent_session.py:101-103`). Do not copy at read sites instead of the constructor — that leaves every other reader to remember the same guard. Add a test asserting a later edit to the caller's original — including an edit *inside* a nested value, not just a new top-level key — does not reach the stored attribute, and that two instances built from the same caller collection do not share state; see `test_the_callers_hints_dict_is_not_aliased` (`tests/test_tool_error_recovery.py:285`) for the flat case, `TestAgentCatalogCopiesTheCallersMaps` (`tests/test_agent_catalog.py`) for the nested-dict case, `TestAgentSessionCopiesTheCallersHistory` (`tests/test_session.py`) for the nested-object case, `test_the_callers_capability_list_is_not_aliased`/`test_two_bundles_built_from_one_list_do_not_share_a_dispatch_set` (`tests/test_tool_error_recovery.py`) for the flat-list-of-live-objects case, and `test_every_list_field_is_detached_from_the_caller` (`tests/test_registry.py:128`) when the dataclass carries more than one list field needing the guard — it reflects over `dataclasses.fields()` to assert every `default_factory=list` field is copied, so a field added later without a matching `__post_init__` line fails a named test rather than drifting silently. When the class also carries a collection field with no `default_factory` (an `Optional[dict[...]]`/`Optional[list[...]]` defaulting to `None`), select by declared type instead — see `test_every_collection_field_is_detached_from_the_caller` (`tests/test_models.py:273`), which reflects via `get_type_hints` and matches any field whose annotation, or any member of its union, has `dict`/`list` as its origin; `default_factory is list` alone misses a `None`-defaulted field. This does not apply to a parameter consumed once and not retained on `self`, to immutable values (`str`, `int`, a frozen dataclass), or to an object that intentionally holds live, caller-shared working state rather than a data snapshot — `AgentRegistry._agents` (`registry/agent_registry.py:87`) was reviewed under #112 and confirmed as a deliberate exception, not a missed site. `AgentContext` (`models/context.py`) was reviewed the same way under #112 and marked the same exception, but that call only holds for `database_connector`; its four other constructor parameters were data, not live state, and #118 corrected the review by copying them — judge each retained field on its own terms, not the class as a whole, when granting this exception. `ToolCallEvent.arguments` (`services/events.py:83-96`) closed under #119, matching `AnswerEvent.sources`'s dataclass-`__post_init__` placement (#116) but using `copy.deepcopy` on both the inbound and outbound halves rather than a shallow `list()` copy, because `arguments` nests further mutable values where `sources` holds opaque flat elements — see the #119 paragraph above for the full comparison. The result-type collections in `models/outputs/__init__.py:25-59` (#125) remain a confirmed pending site under this same class — apply the identical fix (shallow, deep, or whole-object, per the parameter's shape; a `@dataclass` with no hand-written `__init__` needs the copy in `__post_init__` instead, per #113, #116, #117, and #119) when picked up. Issue #120 confirmed the same read-boundary nuance applies beyond a dataclass's own `to_dict()`: a Pydantic-backed catalog's `get()` (or any factory method) that rebuilds a resolved model from a raw stored `dict` must deep-copy that raw block before parsing it out, because Pydantic only rebuilds the containers it declares a type for and stops at `Any` — a value nested inside an `Any`-typed field stays the stored dict's own object across every call. See `AgentCatalog.get()` (`registry/agent_catalog.py:343`), which deep-copies `self._raw_agents[name]` before any field is parsed off it, closing the leak in `tool_rules` and `CapabilityRef.config`, and `ToolCatalog.get()` (`registry/tool_catalog.py:133`), which deep-copies `self._raw_tools[name]` the same way, closing the leak in `ToolMCPConfig.annotations` (#121). `CapabilityRegistry.build()`'s one-level `dict(config) if config else {}` copy before invoking a factory (`registry/capability_registry.py:58-61`, where a nested config value reaches the factory as the caller's own object, #122) remains the confirmed pending site under this same read-boundary nuance — apply the identical whole-block `copy.deepcopy` when picked up. Before shipping a change to a `core/*.py`, `registry/*.py`, or `services/*.py` constructor, `grep -rn 'self\.[a-zA-Z_]* = [a-zA-Z_]* or {}\|self\.[a-zA-Z_]* = [a-zA-Z_]* or \[\]\|self\._\?[a-zA-Z_]* = [a-zA-Z_]*$' sinan_agentic_core/` and confirm no new site stores the bare parameter (or its bare `or {}`/`or []` fallback) instead of a copy. The same detachment applies when a class hands a *retained instance attribute* — not a constructor parameter — out to more than one caller-facing site: copy at each hand-out point, not once centrally, so an edit reaching through one path cannot reach the attribute or another hand-out's copy; see `BaseAgentRunner.last_usage` (`core/base_runner.py:96`), copied separately at `on_fallback_end` (`:520`) and the `answer` event (`:687`) (#124). Before adding a new place that reads a retained instance attribute and passes it to a callback, a hook, or an event payload, check whether another such site already exists for the same attribute — if so, both need their own `copy.deepcopy`, not a copy made once where the attribute is assigned. When a registry or catalog `get`-style read boundary hands back a mutable dataclass record it retains — `AgentRegistry.get()`, `ToolRegistry.get_tool()`, `GuardrailRegistry.get_guardrail()`, and their `*_by_category` siblings — return `dataclasses.replace(record)` rather than the stored object (#149), so `__post_init__`'s container copy re-applies at the read boundary and a reader cannot mutate the process-wide record; only detach the record whose `__post_init__` already copies its containers, so the outbound copy stays consistent with the inbound one. Do not exempt a read boundary because an internal writer patches the record it returns (`ToolCatalog.enrich_registry`): route that writer back through the registry's own `register()` with the patched copy — enrichment is a registry-internal write, not a reader contract. A `frozen=True` snapshot bundle like `ResolvedGuardrails` copies its lists in `__post_init__` via `object.__setattr__(self, "x", list(x))` (#144), since the frozen dataclass forbids `self.x = ...`.
